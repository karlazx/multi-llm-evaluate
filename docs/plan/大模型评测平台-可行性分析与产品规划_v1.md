# 大模型评测平台 — 可行性分析与产品功能规划 v1

> 版本：v1（2026-08-15）｜状态：待老板确认关键假设后细化
> 一句话定位：**一个"用例驱动 + API 自动跑测 + AI 裁判 + 人工复核"的模型选型评测平台**，帮你在每次新模型发布时快速回答："这个模型适不适合我的项目？"

---

## 一、可行性分析

### 1.1 需求与价值判断 ✅ 成立

- **痛点真实存在**：大模型迭代极快（几乎每月有新版本/新旗舰），官方 benchmark 分数（MMLU、GPQA 等）与"在我自己业务上的真实表现"相关性有限。用自己的评估用例测自己的场景，是目前业界公认最可靠的选型方法。
- **现有方案的缺口**：
  | 现有方案 | 局限 |
  |---|---|
  | LMSYS Chatbot Arena / SuperCLUE / OpenCompass 等公开榜单 | 测的是通用能力，不是"你的业务用例"，且无法接入私有场景 |
  | 手工开几个网页逐个试 | 无留痕、无对比、不可复现，新模型一出又得重来 |
  | 脚本裸写调 API | 能用但零散，无裁判评估、无人工复核、无报告沉淀 |
- **差异化价值**：平台化 = 用例资产沉淀 + 跑测自动化 + 评估标准化 + 结论可追溯。每次新模型发布，一键跑完出结论，这是目前公开产品没有覆盖好的"私域评测"场景。

### 1.2 技术可行性 ✅ 可行，核心链路均为成熟技术

| 环节 | 方案 | 成熟度 |
|---|---|---|
| 模型接入 | 主流模型 API 绝大多数兼容 OpenAI Chat Completions 协议（OpenAI/Anthropic/通义/豆包/DeepSeek/GLM/Kimi 等），统一适配层即可覆盖 90% | 高 |
| 用例执行 | 任务队列（并发调用、重试、限流、超时），保存原始产出物 | 高 |
| AI 裁判评估 | "LLM-as-a-Judge"是业界标准做法（MT-Bench、Arena 均采用），用强模型按评分细则（rubric）对产出物打分/对比排序 | 高 |
| 人工评估 | 标注界面 + 盲评（隐藏模型名）+ 与 AI 分数对齐分析 | 高 |
| 报告产出 | 雷达图/排行榜/单用例穿透查看 | 高 |

**结论：没有技术卡点，工程量集中在"评测编排 + 裁判可靠性"两块，不涉及研究性难题。**

### 1.3 主要风险与对策 ⚠️ 需提前设计

| 风险 | 说明 | 对策 |
|---|---|---|
| **裁判偏差** | LLM 裁判有已知偏差：偏长回答（verbosity bias）、偏自己/同家族模型（self-preference）、位置偏差（pairwise 时偏 A 位） | ① 裁判模型与被测模型尽量不同源；② pairwise 对比时随机交换 A/B 位置做两次；③ 提供详细评分细则而非裸打分；④ 定期用人工评估校准裁判 |
| **用例数据污染** | 热门公开题目可能已进模型训练集，测不出真实能力 | 用例以自建/业务真实场景为主，标注"自建/公开"来源，公开题仅作辅助 |
| **评测成本** | N 模型 × M 用例 × （生成 + 裁判）双重调用，费用随规模线性增长 | 跑测前预估 token 成本并提示；支持只跑增量模型；采样跑子集快速摸底 |
| **复现性** | 模型有随机性，且 API 行为随时间变化 | 记录完整快照（模型版本号、参数、时间戳、原始响应）；temperature 等参数默认固定为 0 或用户指定 |
| **版本管理** | 模型悄悄升级导致历史结论失效 | 报告锁定"模型+版本+日期"三元组，新模型触发新一轮评测而非覆盖旧结论 |

### 1.4 结论

**建议立项。** 技术上全部为成熟方案的组合，无硬风险；项目成败取决于两件事：**① 评估用例的质量与覆盖度（这是你的核心资产）；② 裁判评估的可信度设计**。MVP 阶段应把资源集中在这两点上，而不是花哨的平台功能。

## 二、产品功能规划（PRD 概要）

### 2.1 问题陈述

每次有新大模型发布，缺乏一个标准化、可复现的流程来回答"它在我的业务场景下行不行"。靠手工试：慢、无对比、无留痕；靠公开榜单：不贴业务。需要一个平台，把"我的评估用例 → 调模型 API 跑测 → AI+人工评估 → 出选型结论"这条链路自动化、资产化。

### 2.2 目标（v1 成功标准）

1. 新模型发布后，**接入并跑完全量用例出报告 < 30 分钟人工操作**（其余自动）。
2. 每个评测结论都可**穿透追溯到具体用例的原始产出物**。
3. AI 裁判评分与人工评估结论的**一致率 ≥ 80%**（v1 末期校准一次）。
4. 沉淀 ≥ 1 套可复用的业务用例集（由老板提供，平台负责管理）。

### 2.3 非目标（v1 明确不做）

- ❌ 不做公开排行榜/对外服务（先做私有选型工具，是否开放另议）。
- ❌ 不做自动化 benchmark 刷分（MMLU 类选择题批量跑），聚焦开放式业务用例。
- ❌ 不做本地模型部署托管，只调 API（本地模型若有需求，走兼容 API 网关接入，P2）。
- ❌ 不做评测结果的对外分享/SEO 传播。

### 2.4 用户角色（v1）

| 角色 | 职责 |
|---|---|
| 管理员（老板） | 管理用例集、接入模型、发起评测、查看报告、参与人工评估 |
| 标注员（可选邀请） | 仅参与人工盲评打分 |

### 2.5 功能模块与优先级

**P0（MVP 必须有，砍掉就无法成立）**

| 模块 | 功能点 | 验收标准 |
|---|---|---|
| ① 用例管理 | 用例 CRUD；字段：标题、输入（prompt/附件）、评估维度标签、参考答案（可选）、评分细则（可选）、来源标记 | 支持批量导入（JSON/CSV）；用例可停用不删除 |
| ② 模型接入 | 配置 API endpoint / key / 模型名 / 默认参数；连接测试；OpenAI 兼容协议为主 | 一键"测试连接"；key 加密存储，界面脱敏 |
| ③ 评测任务 | 选择用例集 × 模型列表发起任务；并发执行、重试、进度可视；预估并展示 token 成本 | 单用例失败不影响整体；原始响应全量留档 |
| ④ AI 裁判评估 | 指定裁判模型 + 评分细则模板；单点打分模式 + pairwise 对比模式；裁判结果附理由 | 位置交换双跑（pairwise）；输出结构化分数 |
| ⑤ 人工评估 | 盲评界面（隐藏模型名）；打分/排序/写评语；与 AI 分数并列展示 | 同一用例可多人评；支持跳过 |
| ⑥ 评测报告 | 总分排行 + 分维度得分 + 单用例穿透（看原始输出、AI 评语、人工评语） | 报告按"轮次"归档，不覆盖历史 |

**P1（v1.1 快速跟进）**

- 用例版本管理与"用例集"分组（按业务场景：如代码、文案、推理）
- 裁判校准工具：AI 分 vs 人工分的一致性分析面板
- 增量评测：只跑新模型，自动并入历史轮次对比
- 导出报告（Markdown/PDF）
- 评测提醒：订阅关注的新模型发布，触发待办（可配合现有模型追踪简报）

**P2（后续考虑）**

- 多模态用例（图片输入/输出评估）
- 本地/私有模型通过自定义 endpoint 接入
- 团队多租户、权限细分
- 评测用例市场/共享

### 2.6 核心流程

```
管理用例集 → 接入模型API → 创建评测任务(用例集×模型)
   → 自动跑测(留原始产出) → AI裁判评估(打分+理由)
   → 人工盲评(可选校准) → 生成报告(总分+维度+穿透)
   → 沉淀结论 → 新模型发布时增量复测
```

### 2.7 技术选型建议（供参考，可再议）

- 后端：Python（FastAPI）— 模型 SDK 生态最全；任务队列用 Celery/Redis 或轻量 APScheduler。
- 前端：React/Vue 任选，管理台形态，不需要花哨视觉。
- 存储：PostgreSQL（用例/结果/报告）+ 对象存储（原始响应快照）。
- 部署：单机 Docker Compose 起步，够用后再拆。

### 2.8 里程碑建议

| 阶段 | 内容 | 产出 |
|---|---|---|
| M1（约1-2周） | 用例管理 + 模型接入 + 跑测引擎 | 能批量跑测并存下原始产出 |
| M2（约1-2周） | AI 裁判评估 + 报告页 | 首个端到端评测报告 |
| M3（约1周） | 人工盲评 + 一致性校准 | AI/人工双轨结论 |
| M4（持续） | 用真实新模型发布跑一轮，校准用例与裁判 | v1 上线 |

## 三、待澄清的关键问题（请老板拍板）

1. **使用范围**：纯私人选型工具（只有你用），还是未来想开放给其他人/团队用？——决定是否要做账号体系和多租户，v1 建议按"私有工具"做，架构留扩展口。
2. **评估用例的能力维度**：你的项目主要关心哪些维度？（代码 / 中文写作 / 逻辑推理 / 长文本 / Agent工具调用 / 多模态……）以及用例目前有没有现成的，还是要从零建？——这决定 MVP 用例结构的字段设计。
3. **模型接入范围**：只接云端 API（OpenAI 兼容为主）就够，还是必须支持本地部署模型/特殊协议？
4. **裁判模型**：打算固定用一个最强模型当裁判（如当前旗舰多模态模型），还是希望裁判本身也可配置可对比？裁判用强模型意味着每次评测有一笔额外开销，是否接受？
5. **人工评估的定位**：是"每条都人工复核"（重，结论最可信）还是"抽样校准 AI 裁判"（轻，推荐）？
6. **成本预期**：一轮完整评测大概能接受多少 API 费用量级？（影响默认并发、采样策略设计）
7. **时间与开发方式**：期望多久用上 MVP？是你自己开发、我辅助出方案，还是主要由我这边驱动开发？
